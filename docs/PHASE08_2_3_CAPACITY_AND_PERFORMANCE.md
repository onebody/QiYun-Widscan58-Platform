## 1. 口径声明

本文所有数字分两类：

| 类别 | 含义 |
|---|---|
| **结构推导** | 由帧结构常量与固件文档速率计算得出，可复核 |
| **待实测** | 未运行压测/未接真实硬件，**不得当作已验证指标** |

帧大小来自 `repo/firmware/src/proto/frames.h` 与 `repo/rftrack/backend/app/services/frame_parser.py` 的结构定义：

| 帧 | 计算 | 8 频道时负载 | 含 10 B 头 + 4 B CRC |
|---|---|---|---|
| METRICS | `34 + 26 × n` | 242 B | 256 B |
| LEVELS | `32 + 4 × n` | 64 B | 78 B |
| SPECTRUM | `20 + bins`（默认 256） | 276 B | 290 B |
| TELEMETRY | 59 B | 59 B | 73 B |

速率假设（**待实测确认**）：

- C5 8 频道分组扫描，`rotationHz ≈ 60`（每轮 60 次）。
- SPECTRUM 每 4 hop 一帧（默认 `SPEC=4`），约 10–15 帧/s。
- TELEMETRY 约 1 帧/s。

## 2. 场景定义

| 场景 | 节点 | 频道 | 说明 |
|---|---|---|---|
| S1 | 4 | 40+ 目录 | 节点并发仍 ≤8，目录靠时间轮转覆盖 |
| S2 | 8 | 40+ 目录 | 同上，节点数翻倍 |
| S3 | 4 | 8 选中 | 典型对比视图 |
| S4 | 8 | 8 选中 | 上限对比视图 |

> **关键事实**：固件 `PROFILE_MAX_CHANNELS=8`。因此“40+ 频点”在任何场景下都**不是同时观测**，而是“目录 40+、并发 8、按计划轮转”。S1/S2 的单节点帧速率与 S3/S4 **相同**，差别只在频道覆盖的时间分布。

## 3. 单节点数据量（结构推导）

### 3.1 每节点每秒帧数

```
METRICS/s   = rotation_hz × channels = 60 × 8 = 480
SPECTRUM/s  ≈ 12（取 10–15 中位）
TELEMETRY/s = 1
合计        ≈ 493 帧/s
```

### 3.2 每节点每秒字节

```
METRICS   480 × 256 B = 122,880 B/s
SPECTRUM   12 × 290 B =   3,480 B/s
TELEMETRY   1 × 73  B =      73 B/s
合计                  ≈ 126,433 B/s ≈ 123.5 KiB/s ≈ 1.01 Mbps
```

### 3.3 各场景汇总

| 场景 | 节点扫描产出 | Gateway 转发 | Server 写入行数 | Server 写入吞吐（不含索引放大） |
|---|---|---|---|---|
| S1（4 节点） | 4 × 126 KB/s ≈ **504 KB/s** | ≈ 504 KB/s（逐帧转发） | 4 × 493 ≈ **1,972 行/s** | ≈ 1.0–2.0 MB/s（待实测） |
| S2（8 节点） | 8 × 126 KB/s ≈ **1.01 MB/s** | ≈ 1.01 MB/s | 8 × 493 ≈ **3,944 行/s** | ≈ 2.0–4.0 MB/s（待实测） |

> 写入吞吐按每行 JSON 0.5–1 KB 估算，未计索引膨胀、事务开销与 SQLite WAL。

### 3.4 存储增长（原始逐帧）

```
每节点每日行数 = 493 × 86,400 ≈ 42.6 M 行/天
8 节点每日     ≈ 340.8 M 行/天
```

**结论：原始逐帧长期保留不可行。** 现有 `measurements` 表已按帧写入，若 8 节点全量接入，SQLite 单写者会先成为瓶颈。

## 4. 分层容量结论

### 4.1 节点扫描（设备侧）

| 项 | 结论 |
|---|---|
| 单节点帧率 | ~493 帧/s（结构推导） |
| 8 频道并发 | 支持（现有 `CHANNELS` 上限） |
| 40+ 并发 | **不支持**（固件上限 8） |
| 40+ 轮转覆盖 | 需固件扫描调度，`GAP` |
| 扫描与网络并行 | 分离芯片可；同芯片 `UNKNOWN` |

### 4.2 Gateway 转发

| 项 | 结论 |
|---|---|
| 字节量 | 8 节点 ≈ 1 MB/s（≈8 Mbps） |
| 帧处理率 | 8 节点 ≈ 3,944 帧/s（Agent Python 逐帧解码风险高，**待实测**） |
| 现有机制 | 逐帧 `device.frame` 转发，无聚合；测量队列/事件队列分离 |
| 风险 | GIL/JSON 序列化/串口读循环可能先到瓶颈；无基准 |

### 4.3 Server 写入

| 项 | 结论 |
|---|---|
| 行数 | 8 节点 ≈ 3,944 行/s |
| SQLite | **不可持续**（单写者、无批量 COPY） |
| PostgreSQL（未来） | 需批量写入 + 分区；`PROPOSED` |
| 现有索引 | `(device_id, created_at)` 等会放大写入成本 |
| 建议 | 先做写入前聚合（见 §5），再接多节点 |

### 4.4 前端展示

| 视图 | 数据量 | 结论 |
|---|---|---|
| 频谱（8 节点 × 256 bins） | 2,048 点/帧 | 1–2 Hz 刷新可行（待实测） |
| 趋势（4×8=32 系列，24 h @60 s） | 46,080 点 | 可行，建议 max_points 降采样 |
| 趋势（8×8=64 系列，24 h @60 s） | 92,160 点 | **偏高**，建议硬上限 32 线或强制降采样 |
| 热力图（8×8，7 d @1 h） | 10,752 单元格 | 可行 |
| 热力图（8×40，1 h @60 s） | 320 × 60 = 19,200 单元格 | 需横向滚动或降桶 |
| 实时刷新 | 轮询 1–2 s | 现有轮询 5–15 s 不够；WS 为后续 |

## 5. 聚合与保留策略（建议）

### 5.1 写入前聚合

| 数据 | 原始 | 建议保留 |
|---|---|---|
| 频道 RSSI | 480 帧/s/节点 | **1 Hz/频道/节点**（8 行/s/节点） |
| 频谱 | ~12 帧/s | **0.2 Hz**（5 s 一帧）作为快照 |
| TELEMETRY | 1 帧/s | 1 帧/s 或 1/5 s |

8 节点写入：`8 × (8 + 0.2 + 0.2) ≈ 67 行/s` → **5.8 M 行/天**，比逐帧下降约 98%。

| `rf_measurements_1m` | 365 天 | `PROPOSED` |
| `rf_measurements_1h` | 长期 | `PROPOSED` |

> 磁盘容量未实测，不能给出确定 GB 数字；按 1 s 层 64 行/s × 30 d ≈ 166 M 行估算，实际大小待测。

## 7. 容量风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| SQLite 写入瓶颈（8 节点逐帧） | 高 | 写入前聚合；批量事务；迁移 PostgreSQL（另批） |
| Agent Python 帧处理瓶颈 | 高 | 降低上报频率；二进制批量；独立进程（另批） |
| 40+ 频道轮转导致单频道刷新变慢 | 中 | 明确 UI 周期；按需选择 8 频道 |
| 前端 64 系列渲染 | 中 | 硬上限 32 线、降采样、虚拟化 |
| 频谱 bins 存储膨胀 | 中 | 存快照而非逐 bin 行；压缩 |
| 时间戳无墙钟锚点 | 中 | 使用接收时间；补锚点字段（另批） |
| 单网卡多 AP 不可行 | 高 | 明确限制；多射频/节点改 STA |

---

## 8. 结论

1. 单节点 ~1 Mbps、8 节点 ~8 Mbps 的链路量在**网络层**不是主要瓶颈。
2. 真正瓶颈是 **Agent 帧处理** 与 **Server 逐帧写入**，两者均无基准。
3. 必须采用 **写入前聚合 + 分层保留**，否则 8 节点场景不可持续。
4. 40+ 频点在**并发**上不成立，只能“目录 40+、并发 8、时间轮转”。
5. 所有性能数字需在实施阶段用真实硬件与真实数据补齐，届时才能从 `待实测` 改为 `VERIFIED`。
