## 6. Task B — 阶段编号冲突解决方案（三选一，待人工裁定）

### 6.2 方案 B：历史阶段归档

### 6.3 方案 C：建立统一阶段映射（推荐）

不修改任何历史文件名与内容；新增一份权威索引（`docs/PHASE_STATUS_INDEX.md`），逐条记录旧编号、新编号、历史状态、有效性。RF 后续阶段在索引中使用 `RF-P1..RF-P4` 等独立标签。

### 6.4 逐项比较

| 维度 | 方案 A（保留+新编号） | 方案 B（归档+重排） | 方案 C（统一映射） |
|---|---|---|---|
| 历史兼容性 | 高（历史文件不动） | 中（移动文件可能破坏引用） | **高（文件完全不动）** |
| 文档引用影响 | 低（新增编号不影响旧引用） | **高**（移动后旧链接/路径失效） | **无**（只新增索引） |
| 可追溯性（无 Git 环境） | 中（靠文件时间） | 低（移动后时间/路径证据弱化） | **中高（索引+校验和+备份可追溯）** |
| 工程执行风险 | 低 | **中高**（易误引用旧路径） | **低** |
| 维护成本 | 中（两套编号并行，需人工记忆） | 中高（维护归档与新路线双份） | **低（单一索引维护）** |
| 后续阶段清晰度 | 中（08.x 与 RF-x 混用） | 高（旧编号退场） | **高（索引显式声明哪套有效）** |
| 是否需要人工重编号 | 是（新编号体系） | 是（旧→归档） | **否**（仅登记映射） |

### 6.5 推荐意见

**推荐方案 C。** 理由：

1. 仓库**没有 Git**，移动/改名会直接削弱现有的时间与路径证据；
2. 方案 C 不需要人工重编号即可消除“两套 08.3”歧义；
3. 与本次已交付的 `docs/PHASE_STATUS_INDEX.md` 天然一致；
4. 若未来人工决定重编号，方案 C 的索引可直接作为迁移清单。

**但必须明确：**

- 推荐 ≠ 批准。方案 C 的“索引已建立”是文档动作；**“哪套编号为正式有效路线”仍需人工裁定（A10 前置）**。
- 本文件未执行任何改名、移动、归档操作。
