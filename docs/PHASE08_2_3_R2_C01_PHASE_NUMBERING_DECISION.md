### 2.2 为什么不能靠改名/移动消除歧义

1. 无 Git 历史，文件 birth/modify 时间是现有唯一可用的先后证据；移动会改变路径与时间语义。
2. 历史文档已被 `PHASE08_ACCEPTANCE_REPORT.md`、WP-02 报告、`PHASE_STATUS_INDEX.md` 等多处引用，移动会产生断链。
3. 历史 `08.3/08.4/08.5` 的成果（设计 Token、平台 Shell、真实数据接入）客观存在，改名不会改变其“IMPLEMENTED_NOT_ACCEPTED”的验收事实。
4. “未启动”只对 RF 新线成立；对历史线应表述为“已实现、未正式验收”。索引可以把两种语义并存表达清楚。

## 3. 方案 C 的管理规则（正式提案）

> 以下 7 条为方案 C 的管理规则，需人工逐条确认；本轮仅提出，未执行。

| # | 规则 | 说明 |
|---|---|---|
| M-1 | 保留历史 08.1–08.6 的原始编号 | 历史编号继续指向原有文档与实现，不改写 |
| M-2 | 不重命名、不移动、不删除历史文档 | 路径、文件名、内容保持原样 |
| M-3 | 不把历史阶段自动认定为已验收 | 历史线一律保留 `IMPLEMENTED_NOT_ACCEPTED` / `HISTORICAL_DRAFT`，除非人工另行书面验收 |
| M-4 | RF 产品重基线建立独立工作线 | RF 需求/架构/数据/接口/UI 作为独立线管理，不与历史平台 UI 线混用 |
| M-5 | RF 后续阶段编号未最终确定前，使用独立 RF 工作包标识 | 建议 `RF-P1..RF-P4` 等标签；不得占用或改写历史 `08.x` |
| M-6 | 所有阶段状态以 `docs/PHASE_STATUS_INDEX.md` 为统一索引 | 索引为唯一事实源；任何新状态先登记索引 |
| M-7 | 历史阶段与 RF 新工作线之间不自动继承审批状态 | 历史 `APPROVED`（若有）不自动传导给 RF；RF 审批须独立取得 |

**边界声明**：

- M-4/M-5 只是**工作线标签**，不构成对 RF 阶段的正式编号，也不表示任何阶段已启动。
- M-6 的索引登记是文档动作，不构成对“哪套编号为正式有效路线”的裁定。
- M-7 意味着后续任何 RF 审批都必须单独取得，不能引用历史阶段的“完成/通过”作为依据。
