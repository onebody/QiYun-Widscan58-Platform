## ADR-08-01：平台 UI 采用同源零构建静态托管

**问题背景**
平台页面需要一个稳定入口，同时不希望引入第二套前端工程（Node 构建、依赖、CI）。Site Server 已由 FastAPI 提供 REST 与静态托管能力。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 同源原生 HTML/CSS/JS，挂载 `/platform/` | 零构建、零依赖、与 REST 同源、无 CORS、部署简单 | 无组件化、无类型系统、规模增大后维护成本上升 |
| B. 独立 React/Vite 工程 | 工程化完善 | 新增构建链、需处理 CORS/反代、部署复杂度上升 |
| C. 复用 rftrack Workbench | 现成 UI | 数据模型不兼容（site→relay→gateway→node） |

**最终选择**：A。

**理由**
1. 平台定位是“只读运维面板”，7 个页面、无复杂交互，原生足够。
2. 与 REST 同源，天然规避 Phase 07 遗留的 CORS 缺失问题。
3. 不改 `package.json`、不新增锁文件、不影响现有 Console 构建。
4. 可被 FastAPI `StaticFiles` 直接托管，运维只需启动一个服务。

**影响范围**：`site-server/web/*`、`site-server/src/widscan_site/main.py` 挂载逻辑、`docs/PHASE08_4`。

**后续风险**
- 页面数量或交互复杂度增长后，原生 DOM 代码可能变得难以维护；届时需评估迁移到轻量框架（保留同源部署）。
- 无类型系统，字段拼写错误只能在运行时暴露（已由 08.6 实测缓解）。

## ADR-08-02：路由采用 Hash 路由

**问题背景**
静态托管下 SPA 路由若用 History API，需要服务端 fallback（所有未知路径返回 `index.html`），否则刷新详情页会 404。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. Hash 路由（`#/devices/abc`） | 无需服务端 fallback；刷新/分享天然可用；实现极小 | URL 不够“干净”；SEO 无意义（平台无需 SEO） |
| B. History API + fallback 路由 | URL 干净 | 需改 FastAPI 路由；与 `/api`、`/app` 路径冲突风险；部署要求更高 |
| C. 无路由（单页堆叠） | 最简单 | 无法深链接/刷新恢复，不满足需求 |

**最终选择**：A。

**理由**
1. 平台是内网桌面工具，URL 美观无价值；可靠性与零配置优先。
2. `parseHash()` 约 15 行，`hashchange` 即可驱动整页渲染。
3. 不引入服务端 catch-all，避免与现有 `/api/v1/*`、`/ws/*`、`/app/*` 冲突。

**影响范围**：全部平台页面、深链接规范、`docs/PHASE08_2_ROUTE_AND_NAVIGATION.md`。

**后续风险**
- 若未来需要浏览器历史管理（前进/后退语义细化）或外部分享“干净 URL”，需迁移到 History API 并增加 fallback。
- Hash 路由无法使用 `window.history.pushState` 的部分能力（当前无需求）。

## ADR-08-03：RF Console 保持独立应用入口，不内嵌

**问题背景**
原始 widscan58 Console 依赖 Web Serial / WebUSB / Canvas 高频渲染，且已有独立构建（`repo/web/dist`）与 Electron 壳。平台需要提供入口但不能破坏其能力。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 独立入口 `/app/`（新标签页）+ 平台说明页 | 零改造、权限上下文完整、互不影响 | 平台与 Console 无统一导航 |
| B. iframe 内嵌进平台 | 视觉统一 | Web Serial/USB 权限在 iframe 中受限；高频渲染与平台轮询争抢主线程；跨源/同源策略复杂 |
| C. 重写为平台内组件 | “一体化” | 重实现风险极高，可能破坏设备协议路径；违反“不得重实现”约束 |

**最终选择**：A。

**理由**
1. Web Serial/USB 在顶层浏览上下文最稳定，`/app/` 与平台同源但独立文档，权限模型不变。
2. Console 与平台数据平面隔离，切页不影响设备连接。
3. 保留独立运行方式（直接打开 `dist`、Electron `app://`），满足“不得删除独立入口”。

**影响范围**：`site-server` 可选挂载 `/app/`、顶栏入口、`#/console` 说明页、`repo/web`（不修改）。

**后续风险**
- 用户在两个标签页间切换需要自行对照设备；无“从平台带设备打开 Console”的联动（列为规划项）。
- 若未来要求单窗口体验，需重新评估 iframe/WebView 方案与权限兼容性。

## ADR-08-04：实时更新先用固定间隔轮询，不做前端事件流

**问题背景**
Site Server 只提供 Agent 上行 WS（`/ws/v1/agents/connect`），**没有**面向浏览器的 `/ws/v1/site`。平台页面需要“接近实时”的状态。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 固定间隔轮询（5/10/15 s） | 复用现有 REST；零后端改动；实现简单 | 有 5–15 s 延迟；请求量固定 |
| B. 前端 WebSocket 事件流 | 真实时、增量更新 | 后端无端点，需新增推送/订阅/快照补齐，超出本阶段范围 |
| C. SSE | 比 WS 简单 | 同样需新增后端端点 |

**最终选择**：A（B/C 列为 `NOT SUPPORTED`，转规划项）。

**理由**
1. 后端没有事件端点；本阶段不扩后端范围。
2. 运维面板对 5–15 s 延迟可接受；Measurement 查询本身是手动操作。
3. 轮询实现可完全复用 `api()`，错误恢复逻辑统一。

**影响范围**：全部页面的 `{ms}` 返回值、`schedulePoll()`、状态条文案。

**后续风险**
- 数据延迟固定存在；`last_seen_at` 不随帧更新，高频设备活跃度无法体现。
- 轮询在 Agent 数量大幅增长时会增加请求压力；需在引入事件流时替换。
- 当前**无指数退避**，服务持续不可用时仍按固定间隔请求。

## ADR-08-05：状态管理用页面级局部状态 + 请求缓存，不建单一全局 Store

**问题背景**
需要同时管理列表数据、详情数据、过滤条件、系统连接状态，以及 Console 高频射频数据。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 页面级局部状态 + `state.cache`（Map） | 简单、无框架、天然隔离 | 跨页面无共享（当前也不需要） |
| B. 单一全局 Store（含射频数据） | 统一访问 | 高频数据污染全局；渲染耦合；内存风险 |
| C. 引入 Zustand/Redux | 工程化 | 与零构建方案冲突；收益不足 |

**最终选择**：A。

**理由**
1. 平台页面之间只需要传递小参数，用 URL 即可。
2. 高频 RAWIQ/频谱必须与平台状态物理隔离（Console 自持）。
3. 缓存按 key 覆盖，避免长期运行内存增长。

**影响范围**：`app.js` 的 `state`、各页面函数、`docs/PHASE08_2_DATA_FLOW_DESIGN.md` §5。

**后续风险**
- 若未来出现跨页面联动（如“全局选中设备”），需要在 URL 之外引入轻量共享层；不得直接把 Console 数据放入。
- 缓存无 TTL，长期打开同一页可能显示旧值（已有轮询覆盖）。

## ADR-08-06：Measurement 详情用行内展开，不建独立详情页

**问题背景**
用户需要查看单条 Measurement 的 payload；但后端**没有** `GET /api/v1/measurements/{event_id}`。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 表格行内展开 payload | 零新增 API；上下文不丢失；实现小 | 长 payload 占用纵向空间 |
| B. 独立详情页 `#/measurements/:eventId` | 空间充足 | 无单条端点，只能“列表里找”，会出现假路由 |
| C. 弹窗 | 不占表格空间 | 无障碍与滚动体验较差 |

**最终选择**：A。

**理由**
1. 不依赖不存在的端点，避免设计与代码矛盾。
2. `event_id` 已在列表返回，行内即可定位。
3. 展开/收起不影响表格分页状态。

**影响范围**：`buildMeasurementTable()`、`pf-json` 样式、路由文档。

**后续风险**
- 大 payload（如 SPECTRUM/LEVELS）展开后可能很长；08.3 需定义最大高度与滚动策略。
- 若后端后续提供单条详情端点，可再增加深链接路由（届时另立 ADR）。

## ADR-08-07：平台保持只读；权限模型留待后端 RBAC

**问题背景**
Phase 07 已确认 Site Server REST **无鉴权、无 CORS**；Phase 07.2 的设备 owner/observer 授权只在 **Gateway Agent 本地 API** 生效。平台若提供写操作，将放大安全风险。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 平台只读，所有写操作保持 REST/本地 API | 风险最小；与现网能力一致 | 运维便利性不足 |
| B. 前端角色控制 + 隐藏按钮 | 看起来完整 | 前端可篡改；不能替代后端校验（明确禁止） |
| C. 立即实现后端 RBAC + 平台写 UI | 完整 | 超出本阶段范围；需改认证、数据库、部署 |

**最终选择**：A；B 明确禁止；C 列为后续前置。

**理由**
1. 隐藏按钮不构成权限控制；无后端鉴权时写 UI 等于开放写权限。
2. 现有后端写端点（adopt/patch/delete/transfer/revoke/pairing）均无平台级鉴权。
3. 本阶段目标是信息架构，不是权限系统。

**影响范围**：全部页面（无写按钮）、`PHASE08_2_PLATFORM_INFORMATION_ARCHITECTURE.md` §7。

**后续风险**
- 平台长期只读会限制运维效率；需尽快规划后端认证与 RBAC。
- 若后续加入写操作，必须先完成后端授权并补审计日志，否则不得上线。

## ADR-08-08：单站点事实，暂不做 Site 切换器

**问题背景**
任务书建议的层级为多站点平台；但当前 Site Server 是**单实例单站点**：`cfg.site.id` 唯一，`GET /api/v1/site` 返回单条，`GET /api/v1/sites` 为 404。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 单站点常量 + 保留 `?site=` 占位 | 与实际一致；无假控件 | 多站点体验缺失 |
| B. 前端实现多站点切换器（基于假数据/常量） | 视觉完整 | 虚假能力，违反“不得伪造” |
| C. 同步扩展后端多站点 API | 一步到位 | 涉及数据库模型与冻结协议，需人工批准 |

**最终选择**：A；C 需另行批准。

**理由**
1. 单站点是当前**事实**，设计必须如实反映。
2. 假切换器会误导运维判断，且无法真正过滤数据。
3. `?site=` 参数位已保留（Gateways 列表可读），未来可平滑接入。

**影响范围**：Sites 页面、Overview Site 卡、导航、`docs/PHASE08_2_PAGE_FUNCTION_MATRIX.md` 中唯一 `NEW` 项。

**后续风险**
- 多站点需求出现时必须先改数据库/API，属于“需人工批准的扩展”。
- `?site=` 当前无 UI 入口，用户可能不知道其存在（文档需说明）。

## ADR-08-09：Agent 本地命令 API 不映射到平台

**问题背景**
Gateway Agent 提供本地管理 API：`POST /devices/{id}/connect|disconnect|reconnect|commands`、`POST /site-connector/enable|disable|pair`，由 `X-Agent-Token`/Bearer 保护，默认绑定 `127.0.0.1`。平台若代理这些接口，会把本地特权面暴露到浏览器/局域网。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 完全不映射（平台无任何 Agent 命令调用） | 安全边界最清晰 | 平台不能远程操作 Agent |
| B. Site Server 代理（服务端持有 token） | 运维方便 | 需新增鉴权/审计；凭证管理复杂；风险高 |
| C. 浏览器直连 Agent（携带 token） | 少一层 | **凭证会暴露在浏览器**，明确禁止 |

**最终选择**：A；B 需单独安全评审；C 禁止。

**理由**
1. 任务书明确要求“不得在浏览器暴露 Agent 本地命令凭证”“不得把本地 Agent 管理 API 直接映射成公网前端 API”。
2. Agent 默认仅监听本机，说明其定位就是本机运维接口。
3. 当前无平台级认证，代理会形成未授权远程控制面。

**影响范围**：Gateways 页面（无命令入口）、数据流文档、安全边界清单。

**后续风险**
- 远程运维需登录 Agent 主机操作，效率较低。
- 若未来确需远程命令，必须先完成后端认证、授权、审计与最小权限设计。

## ADR-08-10：所有展示数据必须真实，缺失即标注 unavailable

**问题背景**
平台早期容易出现“为了页面完整而硬编码统计数字/假图表”的倾向，会直接误导运维决策。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 只展示真实 API 数据；缺失显式标注原因 | 可信；可审计 | 页面“不完整” |
| B. 缺失项用 0 或示例值 | 视觉完整 | 数据造假，不可接受 |
| C. 缺失项隐藏 | 干净 | 用户误以为能力不存在/已支持 |

**最终选择**：A。

**理由**
1. RF 监测平台的数字直接关联现场判断，造假风险高。
2. 显式 `未实现 / 未提供（原因）` 同时起到“缺口清单”作用。
3. 08.5/08.6 已按此原则实测通过（无 mock 数据）。

**影响范围**：全部页面、`unknown()` 组件、验收标准。

**后续风险**
- 页面观感“朴素”，需要 08.3 用设计语言把“未实现”表达得清晰而不刺眼。
- 用户可能误读 `—` 为 0；08.3 需区分“无数据 / 未提供 / 加载失败”。

## ADR-08-11：不复用 rftrack Workbench

**问题背景**
仓库内存在 `repo/rftrack/frontend/workbench`，外观与“工作台”接近，容易被视为可复用资产。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 独立实现平台 UI | 模型匹配、边界清晰 | 需新写页面 |
| B. 复用 rftrack Workbench | 省开发 | 数据模型不兼容：site→relay→gateway→node vs site→agent→device；字段/状态/权限语义不同 |

**最终选择**：A。

**理由**
1. 两套模型层级与实体语义不同，强行映射会产生错误统计。
2. rftrack 属另一产品线，修改会引入跨产品回归风险。
3. 08.1 审计已确认其不可复用。

**影响范围**：`site-server/web` 的独立实现；不修改 `repo/rftrack`。

**后续风险**
- 两套 UI 长期并存可能造成视觉不一致；08.3 通过共享色彩语义缓解。
- 若未来统一，需要先统一数据模型，属大范围改造。

## ADR-08-12：长标识单行省略 + title，不换行撑高表格

**问题背景**
08.6 验收发现 Measurement 表格中 `event_id` 等长标识使用 `word-break: break-all` 换行，单行高度从 36 px 涨到 71 px，100 行表格严重变形。

**候选方案**

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 单行省略 + `title` 展示完整值 | 行高稳定；完整值可悬停查看 | 需悬停/复制才能读全 |
| B. 强制换行 | 无需悬停 | 行高不稳，表格难以扫描 |
| C. 截断存储（只显示前 N 位） | 最短 | 信息丢失，无法核对 |

**最终选择**：A。

**理由**
1. 表格主要用途是扫描与定位，稳定性优先。
2. `title` 保留完整值，不损失可核对性。
3. 实测行高恢复 36 px，Event ID 列宽 282 → 200 px。

**影响范围**：`truncCell()`、`.pf-trunc`、Measurement/Device 详情表格。

**后续风险**
- 触屏/无悬停环境无法查看完整值；08.3 可定义“点击复制”交互（未实现）。
- 极长 payload 仍走行内展开（ADR-08-06），不受此决策影响。
